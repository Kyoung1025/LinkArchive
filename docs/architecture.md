# Architecture

## Overview

```
[React frontend (Vite + TS)]
      │ POST /links { url }
      ▼
[NestJS API server] ── writes status="pending" to Postgres, returns immediately (no synchronous wait)
      │ push job
      ▼
[Redis queue (BullMQ) — "link-scrape"]
      ▼
[Worker process — separate process/container]
      │ fetch URL → parse Open Graph tags, fallback to <title>/<meta description>
      ├── success → status="completed" + title/description/thumbnail saved
      └── failure → retry up to 3× (exponential backoff) → status="failed" + error_message
      ▼
[Postgres] ◀── both the API server and the worker read/write here directly
      ▲
      │ GET /links polled every 2–3s
[React frontend] shows the status transition pending → processing → completed/failed
```

## Why the API server and the worker are separate processes

Fetching an arbitrary URL and parsing its HTML is slow and unbounded — some sites respond in milliseconds, others take 10+ seconds or hang until a timeout, and a handful will actively fail. If that work happened synchronously inside the `POST /links` handler, the API server's response time would be at the mercy of the slowest external site it happens to be scraping at that moment, and a burst of link saves would tie up request-handling capacity that has nothing to do with the actual bottleneck (network I/O to third-party servers).

Splitting the request into a **write path** (validate the URL, persist `status=pending`, enqueue a job, return `201`) and a **work path** (dequeue, fetch, parse, persist the result) means:

- `POST /links` latency stays roughly constant no matter how slow scraping is, because the API server never waits on it.
- The two halves fail independently. If every worker crashes, links still save (they just sit in `pending` until a worker comes back and drains the queue). If the API server restarts, in-flight scrape jobs in Redis are untouched.
- The two halves scale on different axes: the API server scales with user request volume; the worker scales with queue depth. Coupling them into one process would mean scaling one to compensate for the other.

This is also why the repo is laid out as `backend/api` and `backend/worker` as separate npm packages with separate entrypoints from the very first commit, sharing only `backend/shared` (the Prisma schema/client and a couple of TypeScript interfaces for the job payload) — not because it's required to run them as two `node` processes today, but because that boundary needs to already exist in the code before it can become two Docker images and, later, two Kubernetes Deployments where only the worker's Deployment has a `HorizontalPodAutoscaler` keyed on BullMQ queue length.

## Retry behavior

Scrape jobs are enqueued with BullMQ's built-in `attempts: 3` and `backoff: { type: 'exponential', delay: 2000 }`. Each attempt is logged (attempt number, outcome, and — on failure — the error) so the retry history is visible in the structured logs, not just the final state in the database. Only after the third attempt fails does the worker persist `status=failed` with the error message; between attempts the link stays `processing` while BullMQ holds the job in its delayed state waiting for the backoff window.

## Observability hooks

Both processes are built to be scraped/queried independently, which matters once this runs as separate Kubernetes pods:

- `GET /health` (API only) checks the database and Redis connections independently via `@nestjs/terminus`, so a failing dependency is distinguishable from a failing API process.
- `GET /metrics` exists on **both** processes (API on its main port, worker on a dedicated port, default `9100`) rather than the worker reporting through the API — each worker replica should be scraped as its own Prometheus target once there are multiple of them.
- All logs are JSON with `timestamp`, `level`, `service`, `message`, and relevant IDs (`linkId`, retry attempt), so they can be shipped to a log aggregator (Loki, CloudWatch, etc.) without a parsing step.

## Data model

See [`backend/shared/prisma/schema.prisma`](../backend/shared/prisma/schema.prisma) for the source of truth. `links`, `tags`, and the `link_tags` join table map directly to the schema in the project brief; the `LinkStatus` enum (`pending`/`processing`/`completed`/`failed`) is generated by Prisma and shared between the API and the worker via `backend/shared` so both sides use the same type instead of matching string literals by convention.
